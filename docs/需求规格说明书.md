## 1. 项目背景与目标

### 1.1 项目背景

课程软件项目需要学生共同完成需求分析、分工、开发、问题处理和成果交付。小组讨论中的任务承诺、依赖关系、时间调整和待解决问题，需要与项目记录保持一致。教师还需要依据课程要求和阶段成果了解项目进展。

本系统围绕学生团队的日常协作展开。成员在项目聊天室中讨论，Agent 结合讨论内容和项目数据分析协作事项、补问缺失信息、生成任务与计划草案。团队核对后发布计划，执行中通过进度和讨论反馈调整安排，最后由教师进行阶段检查与验收。

### 1.2 建设目标

1. 建立从课程要求、团队需求到任务、计划和成果的可追踪关系。
2. 为普通成员提供需求讨论、分工反馈、任务推进、问题协作和成果提交的持续使用场景。
3. 让 Agent 实时跟随讨论，主动追问，并生成有来源、可修改、可确认的业务草案。
4. 支持完整初始规划，以及任务延期后的影响分析和计划调整。
5. 以三个阶段衔接学生执行和教师指导，保留提交、反馈、修改和验收历史。
6. 提供清晰的演示数据、操作记录和可复现实验材料，支撑本科毕业设计与论文。

### 1.3 交付目标与范围

本月交付目标包括可运行系统、演示数据、对比实验、部署与使用说明、答辩演示脚本、设计资料和完整论文初稿。具体开发排期在系统设计阶段结合工作量细化。

第一版覆盖教师、组长和成员的完整课程项目流程。任务成果采用文件附件或代码、文档链接提交；任务评论和阻碍记录归入任务协作模块。系统的主要演示入口为学生团队工作区，教师通过课程任务、项目进度和阶段成果进行指导。

本阶段交付本文档。数据库、模型 SDK、文件存储和接口协议的具体选型在后续系统设计中确定，并满足本文档规定的权限、持久化、一致性和异常处理要求。

## 2. 术语与角色

### 2.1 术语

| 术语 | 定义 |
| --- | --- |
| 课程任务 | 教师发布的统一项目要求，包含功能要求、阶段日期、交付物和验收标准 |
| 团队项目 | 学生团队依据课程任务建立的协作空间，拥有独立的成员、需求、任务、聊天室和计划 |
| 项目需求 | 团队对课程要求的细化，记录功能说明、优先级和验收条件 |
| Agent 分析卡片 | Agent 对讨论或项目状态的结构化分析，包含来源、关联对象、待澄清事项或变更草案 |
| 规划草案 | 待核对的任务拆分、成员分工和时间安排，不直接改变已发布的项目计划 |
| 已发布计划 | 组长确认后生效的任务与排期版本 |
| 阶段提交 | 团队针对某个检查阶段提交的材料、项目快照和说明 |
| 可投入时间 | 成员明确提供的、可用于当前项目的时间容量，以小时计，可按周维护 |
| 阻碍 | 影响任务推进的问题，包含描述、关联任务、协作对象和处理结果 |

### 2.2 角色职责

| 角色 | 职责与权限边界 |
| --- | --- |
| 教师 | 管理自己发布的课程任务，查看对应团队的结构化进度、已发布计划与成果，提交阶段检查结果和意见 |
| 组长 | 创建团队项目、邀请成员、协调需求与分工、核对并发布计划、处理整体风险、组织阶段提交 |
| 成员 | 讨论需求、反馈分工和工时、推进本人任务、提出问题、请求协助、提交成果、参与聊天室与草案核对 |
| Agent | 在所属项目内读取允许的数据，分析讨论、主动追问、生成草案、调用约束检查并提出修正建议 |

组长是学生在某个项目中的角色。同一学生可以参与多个项目，并在不同项目中拥有不同职责。账号身份和项目角色由服务端数据决定。

## 3. 业务流程

### 3.1 项目主流程

~~~mermaid
flowchart TD
    A[教师发布课程任务及三个检查阶段] --> B[学生建立团队项目]
    B --> C[维护成员信息并细化需求]
    C --> D[成员在聊天室讨论]
    D --> E[Agent 分析、追问和生成草案]
    E --> F[成员补充、修改和核对]
    F --> G[检查约束并修正草案]
    G --> H[组长确认并发布计划]
    H --> I[成员执行任务、记录进度与阻碍]
    I --> D
    I --> J[团队提交阶段成果]
    J --> K[教师检查并提出意见]
    K --> L{检查结果}
    L -->|需要修改| I
    L -->|阶段通过| M[继续推进下一阶段]
    M --> I
    L -->|最终验收通过| N[项目归档]
~~~

### 3.2 成员日常协作

成员通过个人工作台查看本人任务、相关需求、前置依赖、截止时间和待回复事项。在聊天室或任务评论中讨论问题，更新本人进度、剩余工时和阻碍，提交成果并回应协作反馈。

成员日常推进本人任务不需要逐次经过组长审批。新增任务、调整他人分工或变更整体计划通过草案和团队反馈进入组长确认流程。教师阶段检查与日常任务推进分别记录；“需要修改”表示团队需要整改，不自动阻断日常协作。

### 3.3 三个检查阶段

| 阶段 | 团队提交内容 | 教师检查重点 | 展示数据 |
| --- | --- | --- | --- |
| 需求与计划检查 | 需求清单、任务分工、开发计划和说明材料 | 必做功能覆盖、需求清晰度、分工和排期合理性 | 需求与任务关联、依赖、工作量、阶段排期 |
| 开发中期检查 | 当前进度、阶段成果、阻碍和调整说明 | 已完成内容、主要问题、后续安排 | 任务状态、延期、问题记录、计划版本差异 |
| 最终验收 | 最终代码、报告、测试记录和演示材料 | 课程要求与验收标准是否满足、交付物是否完整 | 成果、测试记录、提交历史和验收意见 |

各阶段的日期和必需材料由教师在课程任务中设置。阶段通过只代表该阶段检查结果，不直接将所有开发任务标记为完成。

## 4. 功能需求

### FR-01 账号与权限

- 用户登录后识别教师或学生身份，并在进入项目时识别组长或成员角色。
- 提供教师、组长、成员的初始化演示账号，具体账号维护方式由系统设计确定。
- 服务端校验资源所属课程、项目及用户权限，不能依赖前端隐藏按钮实现权限控制。
- 访问聊天室和建立实时连接时校验项目成员身份；成员权限变化后，后续访问按最新权限处理。
- Agent 工具和文件访问执行相同的数据范围限制。
- 登录失效或权限不足时给出明确提示，不修改业务数据。

### FR-02 课程任务

- 教师创建课程任务，维护名称、背景说明、必做及选做功能、参考资料、日期、交付物和验收标准。
- 第一版已发布课程任务供已登录学生查看并用于建立团队项目；未发布草稿仅由创建教师访问。
- 设置需求与计划、开发中期、最终验收三个阶段的截止日期与提交要求。
- 草稿可保存，发布前检查必需信息和阶段日期的先后关系。
- 一份课程任务可以关联多个团队项目；教师可以查看这些项目的进度与检查情况。
- 已发布要求发生调整时保留变更记录，供团队核对计划和后续验收依据。

### FR-03 团队项目

- 学生根据课程任务创建项目，创建者成为该项目组长，邀请学生加入团队。
- 维护项目名称、说明、课程任务关联和成员列表。
- 成员维护本人技能标签及可用于当前项目的时间容量；组长可查看并协调。
- 团队项目独立保存需求、任务、讨论、计划、阶段成果和历史记录。
- 项目角色分别判断，不能因用户在另一项目中担任组长而获得当前项目权限。

### FR-04 成员协作

- 成员参与需求讨论，提出或补充需求建议与验收条件；组长整理并确认团队需求。
- 成员对规划草案中的分工、工时和依赖关系反馈意见，提出认领或调整建议。
- 成员查看本人任务及关联需求、前置任务、日期和待澄清事项。
- 支持任务评论、阻碍记录、请求相关成员协助以及记录解决结果。
- 支持提交任务成果、回应检查意见和再次补交材料。
- 分工意见、进度、成果及问题处理保留操作者和时间；记录用于展示实际协作过程，不直接产生自动贡献评分。

### FR-05 任务管理

- 任务至少包含名称、说明、对应需求、验收条件、负责人、预计工时、剩余工时、前置任务、计划日期和状态。
- 已发布任务采用“待开始、进行中、已完成”状态；阻碍作为关联记录，保留出现和解决过程。
- 成员更新本人任务的状态、实际进度、剩余工时、阻碍和成果；组长协调整体安排。
- 聊天中的完成声明可形成待核对建议，实际任务状态通过有权限的业务操作确认。
- 依赖关系只能引用当前项目的有效任务，保存或发布时检查自依赖与循环。
- 展示任务列表、看板、依赖关系和时间安排；显示延期任务与影响因素。
- 已完成任务保留实际记录；如需纠正状态，记录原因、操作者和变更历史。

### FR-06 小组聊天室

- 每个团队项目提供一个聊天室，供本项目学生成员和 Agent 使用。
- 实时展示消息发送者、发送时间和内容，支持关联需求或任务。
- 消息先持久化，成功发送后展示确认状态；发送失败时允许重试并防止产生重复记录。
- 支持读取历史消息，断线重连后补充遗漏消息。
- 展示 Agent 分析、追问和分析卡片，并允许成员继续讨论、补充或纠正信息。
- 人类消息收发与模型调用分别处理，模型等待或失败不阻塞人类聊天。

### FR-07 Agent 分析与追问

- Agent 持续接收讨论上下文，在有界聚合窗口内分析连续消息；持续发言不能使分析无限等待。
- 同一项目对并发输入协调分析，保留尚未处理的消息，避免多次发布相同分析。
- 识别需求建议、任务承诺、负责人、工时、日期、依赖、延期、阻碍、共识和未解决问题。
- 同时查询本项目课程要求、需求、成员容量、任务和当前计划，避免只依据单条消息判断。
- 负责人、工时或时间含义不明确时，在聊天室针对具体事项主动追问。
- 问题关联讨论事项和后续回复，已回答的问题不反复追问；未确定信息保留待澄清状态。
- 相对日期以来源消息时间和项目时区解释，无法确定时追问。
- 分析卡片包含类型、结论或草案、关联对象、来源消息、检查结果及待补充信息。
- 区分讨论中明确的信息、个人建议和待澄清事项；讨论共识与实际业务发布状态分别记录。
- 后续信息改变原结论时更新卡片或标记旧卡片失效，保留变化依据。
- Agent 可自动提出分析和草案，发布任务或计划仍执行 FR-08、FR-09 的核对流程。

### FR-08 智能规划

- 根据课程要求、团队确认的需求、成员信息和已有安排，生成任务拆分、成员分工及时间安排草案。
- 每项任务关联需求与验收条件，提供工时、依赖和日期建议。
- 工时与分工是待确认建议，成员补充或确认后形成可发布草案。
- 草案支持查看、修改、反馈、重新分析和拒绝；保留修改与核对记录。
- 检查必做需求覆盖、依赖循环、依赖时间冲突、工作量超限和阶段超期。
- 结构性需求覆盖按需求与任务关联检查；实际功能是否满足验收条件依据测试与教师检查判断。
- 检查结果指明相关任务及冲突依据，Agent 根据反馈修正草案。
- 使用成员明确提供的当前项目容量与剩余工时，不推断个人日程或读取其他项目的私有任务。
- 技能标签用于辅助分工，最终分工结合成员反馈确定。
- 无可行方案时显示未满足的约束与需要协调的事项，不发布违反约束的计划。
- 组长确认时重新检查权限、数据版本和约束，以一致性操作发布任务与新计划版本。

### FR-09 延期调整

- 成员更新任务进度或讨论中出现延期信息时，Agent 查询实际任务状态和依赖关系。
- 列出受影响的未完成任务、阶段节点及关联成员，说明影响依据。
- 根据剩余工时、成员容量和阶段日期生成调整草案，记录改期、分工或依赖变化的原因。
- 已完成任务保留原记录，正在进行的任务依据剩余工作量调整。
- 课程和阶段截止日期由教师维护，Agent 在这些约束内提出方案。
- 调整草案经过成员反馈、约束检查和组长确认后发布。
- 保留旧计划与新计划，可比较负责人、时间、工时、依赖和任务变化。
- 无可行方案时记录风险，供组长与教师协调，不修改教师设置的截止日期。

### FR-10 阶段检查与展示

- 团队查看三个阶段的截止日期、必需材料和当前检查状态。
- 组长汇总成员成果提交阶段材料，保存提交时的计划版本和结构化进度快照。
- 教师查看材料，记录“通过”或“需要修改”，并填写具体意见。
- 修改后重新提交，保留每次材料版本、提交者、时间及相应审核意见。
- 学生与教师查看允许范围内的进度、任务完成情况、成员工作量、计划差异和阶段结果。
- 指标显示计算口径与统计范围；任务完成比例只表示任务状态，不直接等同功能完成、课程验收或成员贡献。
- 教师结果页面不包含聊天室入口、原始消息和内部 Agent 卡片内容。

## 5. 状态与一致性规则

### 5.1 状态约定

| 对象 | 状态或结果 | 规则 |
| --- | --- | --- |
| 课程任务 | 草稿、已发布、已归档 | 发布前检查要求与阶段日期；归档保留历史 |
| 团队项目 | 准备中、进行中、已归档 | 首次计划发布后进入执行；最终验收通过后可归档 |
| 开发任务 | 待开始、进行中、已完成 | 阻碍、成果和纠正记录与状态分别保存 |
| Agent 分析 | 分析中、等待补充、已生成、失败 | 无需变更的分析可结束，不强制生成任务 |
| 规划草案 | 待核对、可发布、已发布、已拒绝、已失效 | 发布要求核对与约束检查通过；失效草案重新核对 |
| 阶段检查 | 未提交、待审核、通过、需要修改 | 重新提交进入待审核，历史提交和意见保留 |

### 5.2 发布与并发规则

1. Agent 生成的草案与已发布任务、计划分别保存。
2. 确认草案时比较其依据的数据与当前项目状态；相关状态已变化时提示重新核对或分析。
3. 同一草案的重复确认只返回原发布结果，不能重复创建任务或计划版本。
4. 任务变更与对应计划版本一致提交；失败时不保留部分生效的变更。
5. 无效的成员、任务、需求或消息引用不能进入已发布业务数据。
6. 新信息纠正旧建议时保留来源和处理记录，失效建议不能直接发布。

## 6. 核心数据需求

下表定义概念对象与最小信息，具体表结构、索引和存储方式在系统设计中确定。

| 对象 | 最小信息与关系 |
| --- | --- |
| 用户 | 身份、登录信息、显示名称；项目角色通过成员关系确定 |
| 课程任务 | 发布教师、说明、功能要求、资料、阶段要求、验收标准及变更记录 |
| 团队项目 | 课程任务、名称、组长、成员、项目状态 |
| 项目成员 | 所属项目、用户、项目角色、技能、可投入时间 |
| 项目需求 | 所属项目、课程要求关联、说明、优先级、验收条件、确认记录 |
| 开发任务 | 所属项目、需求、负责人、工时、日期、状态、成果与变更记录 |
| 任务依赖 | 同项目的前置任务与后续任务 |
| 协作记录 | 所属任务或需求、评论或阻碍、操作者、时间、处理结果 |
| 聊天消息 | 所属项目、发送者、时间、内容、关联对象、发送确认标识 |
| Agent 分析卡片 | 所属项目、来源消息、类型、分析、问题、关联对象、依据与状态 |
| 规划草案 | 项目、来源卡片、基础数据版本、建议变更、约束结果、反馈和发布结果 |
| 计划版本 | 项目、版本、基于前版的变更、确认人、时间和发布时的任务快照 |
| 阶段提交 | 项目、阶段、提交版本、材料、说明、进度快照、计划版本、提交者和时间 |
| 教师审核 | 阶段提交、教师、检查结果、意见和时间 |
| Agent 运行记录 | 项目、输入消息范围、模型与提示版本、工具执行结果、耗时、失败信息及可用的用量数据 |

课程任务对应多个团队项目；项目内对象按项目隔离。任务依赖、分析消息引用和草案对象必须属于同一项目。时间记录采用统一标准，界面按 Asia/Shanghai 展示。

## 7. 异常处理需求

| 异常 | 系统行为 |
| --- | --- |
| 模型未配置或接口不可用 | 标明 AI 不可用，保留待处理输入；人工聊天和业务操作继续可用 |
| 模型超时或调用失败 | 展示失败状态，允许有权限的成员重试；重试不重复发布业务数据 |
| 模型返回格式或引用错误 | 校验并拒绝不合法草案，保留失败原因，允许重新分析 |
| 缺少负责人、工时或时间信息 | 针对该事项追问；未补齐部分保留待澄清状态 |
| 需求或时间约束无可行安排 | 列出冲突及协调事项，保留已有有效计划 |
| 聊天断线或发送失败 | 提示连接状态，重连后恢复历史，重发避免重复消息 |
| 草案过期或重复确认 | 过期草案重新核对；重复确认返回原结果 |
| 用户权限失效 | 拒绝后续访问和操作，提示重新登录或权限不足 |
| 引用对象被修改或失效 | 提示重新检查，防止无效引用进入已发布计划 |
| 阶段材料不完整 | 标明缺少材料，补齐后提交；保留已有材料和历史 |
| 发布过程中持久化失败 | 返回失败结果，保持原计划与任务状态一致 |

模型的超时、聚合窗口和有限修正次数作为可配置运行参数，具体默认值在系统设计中结合接口条件确定。

## 8. 非功能需求

### NFR-01 权限与凭据

- 按教师所负责课程、项目成员关系及操作者权限校验所有访问。
- 教师、其他团队成员和无权限用户不能通过接口、实时连接、文件或 Agent 工具绕过聊天室限制。
- 模型凭据仅由服务端读取，不发送给前端；日志、错误信息和导出材料不包含密钥或密码。
- 成员、任务、需求等引用在服务端校验，模型生成的引用不能直接视为有效数据。

### NFR-02 响应与恢复

- 人类消息接收、持久化和广播独立于 Agent 调用处理。
- 界面展示连接、发送、分析和失败状态，避免把等待状态表现为操作成功。
- 聊天消息、任务、计划、阶段提交和审核记录在服务重启后可恢复。
- 提供演示数据初始化、备份恢复和启动说明。

### NFR-03 可追踪性

- 业务变更记录操作者、时间、原因及关联对象。
- Agent 卡片保留消息出处、依据和修正记录；按权限展示来源。
- 计划版本和阶段提交保留当时快照，后续更新不覆盖历史检查依据。
- 运行记录保存模型、提示与样例版本、耗时和可用的用量信息；缺失的接口用量标记为未知，不记为零。

### NFR-04 可用性与展示

- 学生工作区关联聊天室、需求、任务、计划和阶段成果，便于从消息定位相关业务数据。
- 普通成员可完成需求反馈、本人任务推进、阻碍处理和成果提交。
- 教师端聚焦课程任务、团队进度和三阶段检查。
- 首版以桌面浏览器使用和多账号演示为主要场景，页面可清晰呈现状态及调整前后变化。
- 演示数据标注为测试或演示用途；保留真实模型输出，不以预制内容冒充在线分析或实验结果。

## 9. 验收标准与需求追踪

验收准备至少包含一名教师、两个团队，以及各团队的组长和成员；使用独立账号和明确标注的演示数据。涉及 Agent 的功能验收连接真实模型接口，异常场景允许使用受控测试替身。

| 编号 | 关联需求 | 场景与通过条件 |
| --- | --- | --- |
| AC-01 | FR-01、FR-02、FR-03 | 学生不能查看教师未发布草稿；教师发布一份包含三个检查阶段的课程任务后，两个团队建立独立项目并查看课程要求 |
| AC-02 | FR-01、NFR-01 | 其他团队成员通过页面、接口或实时连接访问项目数据时被拒绝，Agent 上下文也不含其他团队私有内容 |
| AC-03 | FR-01、FR-04、FR-05 | 成员能更新本人任务、工时、阻碍和成果；擅自修改他人分工或发布整体计划时被拒绝 |
| AC-04 | FR-06、NFR-02 | 多名成员实时发送消息，其他在线成员收到且历史可读取；重连补齐遗漏消息，重试不重复保存 |
| AC-05 | FR-07 | 从独立测试讨论中提取任务建议；负责人或工时缺失时主动追问，回复后更新关联卡片并保留出处 |
| AC-06 | FR-07 | 连续发言期间仍会产生分析；同一事项不重复生成卡片或反复追问已回答问题 |
| AC-07 | FR-08 | 草案包含任务拆分、负责人、工时、依赖及排期；任务可以追溯到需求和验收条件 |
| AC-08 | FR-08 | 构造需求遗漏、循环依赖、依赖时间冲突、容量超限和阶段超期样例，系统报告相关对象与依据并允许修正 |
| AC-09 | FR-08、5.2 | 核对与检查通过后，组长确认发布新计划；重复确认不重复创建任务，成员不能越权发布 |

| AC-11 | FR-07、FR-09、5.2 | 后续讨论纠正负责人或日期时，旧建议更新或失效；相关业务状态变化后的过期草案不能直接发布 |

## 10. 对比实验与论文支撑

### 10.1 研究问题

研究结合项目上下文、工具查询和约束检查后，讨论信息提取及任务规划结果是否更有效。改进效果由实际实验判断，保留无改善和失败案例。

### 10.2 实验要求

- 采用固定的讨论样例及其初始项目状态，覆盖需求提取、缺失信息、分工、依赖、延期、纠正和不可行安排。
- 开发调试样例与最终评价样例分别管理，评价样例事先标注应识别事项和可检查约束。
- 对照方法包括仅根据聊天内容生成任务与计划，以及结合项目上下文、工具和约束反馈生成结果的方法。
- 使用相同模型和对应测试输入，记录信息范围、提示、运行参数和调用预算的差异。
- 上述整体对比包含信息范围差异，结论限定为整体方案效果；如需单独评价约束反馈的作用，补充同等上下文下的对照。
- 对多次运行保留独立结果，说明样例数量、评价口径和运行次数；具体规模依据实际调用预算在实验设计中确定。
- 保存原始样例、标注、项目状态、请求配置、工具结果、输出及评分记录。

### 10.3 指标与解释

| 指标 | 记录要求 |
| --- | --- |
| 任务提取质量 | 核对任务、负责人、日期、工时及依赖，记录正确、遗漏和错误项，说明自然语言匹配口径 |
| 信息补全情况 | 记录必要问题是否提出、回复是否正确关联，以及重复追问情况 |
| 约束满足情况 | 对可检查约束逐项统计，分别报告约束通过比例和全部必需约束通过的计划比例 |
| 建议重复与遗漏 | 记录重复任务、失效建议和未处理的协作事项 |
| 响应时间 | 分别记录消息处理与 Agent 分析耗时，注明运行环境和模型条件 |
| 调用成本 | 记录请求次数、接口可用的用量与实际计费依据；无法获得的指标标记未知 |

### 10.4 论文材料

论文资料覆盖背景与相关工作、角色和需求分析、系统与数据设计、实现过程、Agent 协作方法、功能与权限测试、对比实验和实际局限。

系统开发期间同步保存需求变更、架构及数据关系图、主要页面截图、操作记录、模型与提示版本、测试及实验原始结果。相关工作引用原始资料，文稿中的性能或准确性结论与实际记录对应。

## 11. 演示案例与交付检查

### 11.1 完整演示案例

1. 教师发布课程任务及三个阶段要求，学生建立团队项目。
2. 成员填写技能和可投入时间，细化一组项目需求。
3. 成员在聊天室讨论任务，刻意遗漏一项负责人或工时信息。
4. Agent 主动追问，成员回复后形成完整任务与计划草案。
5. 展示一项容量或依赖冲突，以及约束检查和修正结果。
6. 团队核对、组长发布，在任务表、看板和时间安排中查看对应数据。
7. 成员更新进度并报告延期，展示影响分析、新草案和计划版本对比。
8. 团队提交阶段成果，教师检查并给出意见，学生修改后重新提交。
9. 展示另一个团队及教师账号的访问范围，验证聊天室和内部卡片隔离。
