# Agent 可靠性改进说明

本轮围绕历史真实评价中的超时、缺失信息补造和原样旧任务输出修复生产实现。公共卡片字段、组长发布流程及数据库结构沿用现有契约；新评价与历史评价分开保存，结果见 [Agent 可靠性独立复验](Agent可靠性复验.md)。

首轮 24 项真实评价还暴露了供应商将内部 `analysis` 对象编码为 JSON 字符串的兼容问题。首轮结束后，交付代码仅增加该字段完整解码一层，再执行原严格校验；原源码、原锁和原分数都保留。离线回放和修订后单次真实追问联调分开记录，不能合并为修订版的新成功率。当前免费模型仍可能超时，成员核对与人工备用草案继续保留。

## 从讨论到草案

后台先提供所属项目的课程要求、已确认需求、成员容量、任务及待核对卡片。上下文完整时，模型只需选择 `check_plan` 或内部 `finalize_analysis`；信息确实不完整时才开放项目查询工具。完成工具只提交草案，不具有发布或数据库写入权限。

`finalize_analysis` 接收公开分析结构及内部 `task_evidence`。一份合法提交在服务端完成来源和约束核对后即可结束，减少为了“最后再说一句”额外请求模型的情况。精确相同的约束检查结果在单次分析内复用；完成一次有效检查后只提供完成工具，避免重复查询或检查。

新任务的负责人、预计工时、开始和截止日期需要引用本次真实人类消息的原文，或者明确引用被更正卡片的同键任务并有沿用承诺。非初始任务状态下，剩余工时也需独立依据。核对以明确的任务原名和可唯一继承的讨论主题为范围，不能借用另一项任务的承诺。否定、条件、候选负责人和不明确日期不直接确认为事实。

核对支持明确姓名、自荐、常用中文或数字工时、绝对日期、上海时区相对日与明确日期区间。这是一组保守的语法检查，尚不能理解任意改名、同义改写或复杂语义。无法确认时整份变更退回具体追问，标题和摘要也改为待确认表述，避免在摘要中继续声称已确定分工。成员仍需核对，组长仍需显式发布。

## 约束与失败处理

先校验来源、稳定任务标识及重复标识，再将与初始快照逐字段完全一致的现有任务移除。真正修改了已完成任务、非法引用或依赖的项目继续交给共享 `check_plan` 拒绝，不能通过删除错误字段绕过检查。移除未变任务后没有实际变更时，不生成新的正式任务。

响应只接受完整 JSON 或单一完整 JSON 代码围栏，不从混合说明文本中猜测截取。最多两次结构修正，共享每次分析最多六个模型请求的预算；反馈仅提供字段位置与错误类型。网络、权限、来源及数据库错误不作为格式修正自动重试。外层模型分析默认 60 秒，失败不影响人工聊天、任务推进或阶段审核。

## 评价与证据边界

独立新评价比较归档 v2 和当前 v3 的完整方案，统一上下文、消息、免费型号、温度及请求和时间预算。冻结的六个评价例各重复两次，每组 12 项；开发例不进入成功率。程序输出与原始模型提交分别计数，不能把服务端拦住的补造描述为模型没有犯错。

实验客户端显式禁止自动跟随重定向，SDK 重试为零。每次请求、响应、用量和工具结果先保存逐项快照，再更新整轮记录；离线恢复先核对身份、输入哈希和证据单调扩展，冲突时停止且不改盘。未知费用或 token 记为未知，失败保留，不能只展示成功项。

历史结果仍在 `experiments/results/eval-live-20261015-v2/`；新结果位于 `experiments/reliability_v3/results/` 的明确真实运行子目录。两轮样例和指标不同，不能把旧 7/20 与新比例直接相减，也不能据此声称学习成绩或长期团队效率提高。
