# 独立 v3 可靠性评价协议

本协议和 3 个开发、6 个评价样例在看到任何新真实模型输出前固定。旧实验的样例、记录、锁和 7/20 指标保持原样；新指标不能直接与旧严格成功率作数值比较。

## 比较范围

比较 `baseline_v2` 与 `improved_v3` 两套完整方案。旧版从只读 `baseline/agent.py` 加载为 `app.agent_v2_frozen`，相对导入使用当前 `app` 公共模块。每次加载前核对归档 7 份源码 SHA，且当前 schemas、planning、models、serializers、database、permissions 六份源码必须与归档 manifest 相同。归档 SHA 也纳入新锁；不导入 `app.main`，不构造或 prepare Settings。

两组都获得同一个真实 ProjectTools 序列化的完整初始 context 和相同消息。输入 SHA 按相同 JSON 规范计算；只有版本提示与内部工具方案不同。这属于整体方案比较，不能归因于“纯工具作用”。温度 0.2，单项总时限 60 秒，每项最多 6 请求，SDK 重试 0。6 例 × 2 组 × 2 次 = 24 项，最坏 144 模型请求。全局预算最多 180，并受实时可核验免费配额进一步限制。

顺序按固定 seed=20261020 轮转交错：每一重复内按样例排列，每例两组相邻，组先后随例号及重复号交替。不会先跑完某组再跑另一组。每项重新创建独立 SQLite 内存库，用真实 ProjectTools 和 check_plan，绝不接触正式数据。

## 冻结样例

业务项目为“实验室设备借用平台”，学生为周辰(21)、林悦(22)、孙浩(23)，教师为唐老师(2)。需求 ID 421–424，原任务 631–633，消息 ID 从 821 开始。所有消息来源时间固定为 Asia/Shanghai 的 2026-10-20 09:00 起；多条消息相隔一分钟。设备目录发布已于 10-16 完成，阶段期限为 10-16、11-04、11-18，容量与预期排程相容。

| 样例 | 触发事实 | 预先真值 |
| --- | --- | --- |
| V3E01 | 孙浩新增操作视频，3h，10-22 至 10-23，依赖完成项631 | 仅一个新任务，关联421，验收覆盖查找设备、提交预约；保护631 |
| V3E02 | 只给短信验证验收条件 | tasks为空；问负责人、预计/剩余工时、开始、截止 |
| V3E03 | 两条消息给孙浩、3h、10-26开始、无前置及验收，截止未定 | tasks为空；只需问截止；额外追问另计 |
| V3E04 | 林悦本人自荐，中文“两小时”，今天开始明天交付，明确实现联调阶段 | 新盘点核对，关联421，负责人22，2h，10-20 至 10-21，依赖631，阶段1 |
| V3E05 | task633比前置排得早，要求第一个工作日开工、两个工作日，其他原字段保持 | 仅633改为10-22 至10-23，完成631与其他原任务保持 |
| V3E06 | task632延期到周五10-23，其余原字段保持；后续两个工作日、首个工作日启动 | 632仅截止改10-23，633为10-26 至10-27；其余字段保持，完成631保持 |

3 个开发例为标签打印完整新增、负载测试仅缺工时、既有任务负责人更正。开发集与评价集分别导出。模型输入只由 mode/context/messages 构造，不包含 expected、aliases、字段标签、问题标签或 offline_fixture。

标题必须匹配冻结的规范化完整别名，不以描述代替标题；明示保持原字段的任务另将原 title 作为精确事实，因此别名不能掩盖不被允许的改名。E01验收词组预先包含查找/查询/搜索和提交/发起等义词，并预先拒绝“不得查找/提交”等明确否定；E04预先拒绝“不一致”等相反关系。此规则仍是有限标签匹配，不声称完整自然语言蕴含判断。日期使用 `one_of` 显式枚举允许值；当前每项日期只有一个合法值。无须模型猜测唯一默认阶段：E01/D01未明示阶段，stage_index 不计入字段命中，但仍须通过真实阶段截止约束。E04明确阶段；既有任务明确保持阶段的样例按原值计分。

否定作用域仅处理已登记的局部边界：E01拒绝词须直接修饰查找/提交等动作（可含列明副词），因此“不允许跳过提交预约步骤”不当作禁止提交；E04分句“如不一致则验收不通过”属于失败条件，预先从正向验收匹配范围排除，余下部分仍须满足正向词组，不能仅凭失败条件判验收正确。原来的“不得查找/提交”和直接“不一致”反例仍拒绝。机械规则仍可能误判未列明的条件句、转折、否定嵌套和复杂等义表达；不据此宣称完整语义正确，也不在看到真实输出后扩大规则。

## 评分顺序与指标

主指标评价生产 provider 最终公共 `output`，代表完整版本方案的可用行为。实际保存的最后模型响应另解析为 `raw_submission`：finalize_analysis.arguments.analysis 或最后响应 content 中的纯 JSON，也接受包住完整 content 的唯一 `json` 或无语言标记代码围栏；可从该 JSON 的 `analysis` 包装字段提取。纯解析只解码真实保存的原始内容，不调用 provider 的业务规范化，不从夹杂说明中截取 JSON，不接受多个围栏，也不用公共 output 回填。没有真实响应/提交或解析失败时保持null。原模型候选以 `raw_model_*` 单列，不能用已被生产事实关卡安全转为追问的原候选去否决正确公共结果。两组在同一层使用同一评分器。公共结果也保留自身未变任务计数，允许直接衡量新版消除冗余的效果。

1. 用同一公共 AgentOutput 验证公共返回值。`kind` 必须是 schema 允许的 `discussion`、`plan` 或 `adjust`；`kind_ok` 只诊断其是否与输入 mode 相同，不作为 semantic_success 或 strict_success 的成功门禁。例如 mode=plan 的 E02 可以用 kind=discussion 返回空任务和全部四类追问。`None`、格式错误或 schema 错误不能转成成功。provider真的因来源/duplicate/修改done失败时，output仍失败，不靠下游等价过滤洗白。
2. 公共输出先检查来源真实性及完整性、重复来源、重复 key、重复 existing_id、重复依赖和真实 check_plan 约束。所有已完成任务的实体字段必须保持原样。错 ID、真正修改完成项和重复 key 必须保留失败，不能先过滤隐藏。
3. 只对引用合法、所有序列化业务字段相同的旧任务做精确等价过滤；依赖顺序不影响等价。单独记录该层原始任务数、未变旧任务数和 changes_only_contract；原模型层用 raw_model_* 独立记录同类指标。原样带出旧任务属于冗余输出，不称为“篡改”。
4. 在有效变更上按预先别名匹配任务，比较预先事实字段、日期允许集及验收词组。明示保持的原字段按其已有值比较。未匹配或重复匹配任务计作 hallucinated_tasks；这是一项机械“多余/无标签任务”指标，不等同于主观判断全部为编造。
5. **semantic_success**：schema、来源、标识、完成实体、约束、任务与字段全部正确；计划场景必须有有效变更且 questions 为空，任何未解决问题都会阻止真实发布，因此该场景有额外问题即语义失败；缺信息场景必须 tasks 为空且问到全部所缺标签，额外问题仅影响严格指标。来源必须恰好覆盖本次全部人类消息，无重复。
6. **strict_success**：semantic_success 成立，公共输出没有原样未变旧任务、额外问题主题、未知问题或重复问题；原模型候选还必须通过schema/来源/标识/完成保护/约束，且无原样未变旧任务、缺信息仍补任务或无标签任务。额外追问独立计数；E03问了截止又问负责人/工时可 semantic 成功，但 strict 失败。原模型编造一个任务、被生产事实关卡转成正确四类追问时，semantic可成功、strict失败，raw_model_*忠实保留原候选问题。

问题主题由冻结正则识别，包括负责人、工时、开始、截止、验收、阶段、依赖和关联需求。一个问题可覆盖多个主题；额外主题和无法识别的问题分别计数。该规则可能低估未枚举的中文等义表达。人工复核可另存意见，不得回改标签或机械分数。

另列：原始输出契约、完成实体保护、约束通过次数、原样旧任务数、缺信息仍输出任务的错误、额外追问、调用次数、耗时、tokens、费用。未运行单列 not_run；真实尝试中的网络、超时、格式及 None 输出失败全部进入 attempted 分母。缺失 tokens/cost 为 null；已知部分也不能假设未知部分为0。

## 执行与证据

默认 dry-run，不读取环境凭据、不构造 SDK。只有 --live 读取进程 `LLM_API_KEY` 或 `OPENROUTER_API_KEY`、`LLM_MODEL`、可选 `LLM_BASE_URL`。不读取 .env、jwt.key 或正式 data。真实接口只允许 OpenRouter HTTPS 固定端点；复用旧 transport 的 Budget、RecordingCreate、RecordingTools、preflight、redacted，不改旧文件。

两组评价器通过同一个默认工厂构造显式 `DefaultAsyncHttpxClient(follow_redirects=False)` 和 SDK 客户端，共用原模型、Key、base URL、60 秒超时与重试0；provider 先以 ai_ready=False 冷启动，避免先创建 SDK 默认跟随重定向的客户端。307/308 等重定向按当次失败保存，不自动发出第二个 POST，因此不能绕过请求预算；显式注入的离线 provider 保留自己的本地传输。

先核验模型当前全部报价为0、免费请求剩余额度为已知正整数；任何未知或非零报价立即停，不换模型、不回退付费。每次 SDK 请求通过 extra_body 限制全类型零价及禁回退，失败也消费预算；接口报告非零实际费用即停止。未知费用仍是null。

manifest 保存环境、模型、预算、协议、源码、基线和样例 SHA；cases 保存同轮标签快照；records 保存完整计划与逐项状态；attempts 保存每项完整快照；summary 保存离线聚合。每个请求在发出前和结束后原子替换保存，每个生产工具结束后也原子保存。响应未返回时 response 必须保持 null。异常或中断保留完整计划，不删失败、不填补响应。

checkpoint 按 attempt、records、manifest 顺序原子替换；若在两次替换间中断，以先提交的逐项 attempt 作为恢复来源。离线恢复先校验整轮计划、文件名、job_id/case/group/repetition 和真实序列化 common_input 的内容与 SHA，再要求 attempt 对 records 的请求/工具列表是单调扩展：已有请求序号和请求参数、工具名称和参数必须完全相同，已有非 null 的响应、usage、费用、工具结果和其他字段不得丢失或替换；只允许未定字段补为已保存的真实值和追加后续记录。不按 mtime 盲选；身份、输入、前缀或已知证据冲突时，在任何文件写入前停止并保留全部文件。

`--summarize` 仅聚合已保存终态 score，不发请求。先恢复已保存的 response/usage/工具结果，仍为 running 的项转为真实中断失败并重新计算失败评分；未收到的响应继续为 null，不从公共 output 编造。已完整提交的 completed/invalid/failed attempt 保留真实终态和已有评分，不重新评分；恢复或采用更完整快照要求源码协议 SHA 一致。完整性按所有计划项终态判断，平衡性按样例和重复号逐项匹配判断。只有完整、平衡、live 的6例×2组×2重复评价才允许排名。

新 freeze.json 只位于本目录，涵盖 case/runner/scorer/state/loader、公共依赖、当前 production agent.py 与 agent_output.py、归档 baseline、共享 transport 和本协议 SHA。主代理完成独立规格与质量双审后才统一真实运行。`offline_oracle`、HTTP stub 和临时测试产物只能验证程序，绝不作为真实实验结果。
