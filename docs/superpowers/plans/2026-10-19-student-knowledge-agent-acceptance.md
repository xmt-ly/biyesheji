# P3：团队知识、Agent诊断与综合验收实现计划

> **面向 AI 代理的工作者：** 使用 subagent-driven-development 或 executing-plans 逐任务实现；P1/P2基础数据可核对后开始。本计划编写不触发模型请求或自动开发。

**目标：** 学生能查询本项目已确认知识与决策，得到引用真实来源的回答和协作诊断，并完成新功能的实际验收、论文与交付收尾。

**架构：** 知识记录先由人确认和版本化，再按项目检索；规则生成诊断事实，模型负责解释与追问。新知识/诊断输出结构与原任务规划协议分开，模型不直接发布知识、改任务或通过互审。

**技术栈：** 既有关系数据库、Python关键词检索、现有OpenAI兼容客户端、Vue；本版不增加向量数据库、联网搜索或自动代码仓库读取。

---

覆盖STU-04、AI-01以及所有新功能的综合验收。现有任务规划Agent可靠性待办继续独立推进，不以本批问答/诊断成绩替代其原评价。

## 任务1：知识与决策的确认、版本和来源

条目包括接口约定、需求说明、协作约定和决策记录。学生可以提出草稿，作者可改本人草稿，组长确认当前结论。确认后新内容生成新版本；旧版本保留并标superseded/retracted，不覆盖原文。

来源可以是本项目已确认需求、计划版本、可访问成果或明确选择的聊天片段。保存来源对象、版本、内容摘要与指纹；聊天关联不自动变成已确认决策。未确认内容展示为建议，默认不作为确定回答依据。

- [ ] **步骤1：写失败测试。** 成员提出草稿、组长确认、新版本取代旧版本；普通成员不能确认或改他人条目；跨项目引用、自报不存在来源、教师访问内部知识均拒绝。
- [ ] **步骤2：运行。** `python -m pytest backend/tests/test_student_knowledge.py -k version -q`，预期模型和路由缺失。
- [ ] **步骤3：实现。** v004迁移及`GET/POST /api/projects/{id}/knowledge`、`POST /api/knowledge/{id}/versions`、`confirm/retract`动作。关联内容在服务端重取并核对可访问性，内容修改保留原引用指纹。
- [ ] **步骤4：验证前端。** KnowledgeView区分草稿/当前确认/历史版本，可查看来源及为何修改；`node --test frontend/tests/studentKnowledge.test.mjs`覆盖更正、撤回、失效来源和权限。
- [ ] **步骤5：提交。** `feat(知识): 保存团队知识与决策版本来源`。

## 任务2：项目资料与历史决策问答

先建设无模型检索：在本项目有效确认条目上做标题、关键词和正文匹配，按确定规则排序，最多返回8个片段，每片段最多2000字符；中文可按规范化后的双字片段匹配，不安装额外分词或向量服务。该版本可能召回不足，查不到时明确未知。

默认查询当前确认版本；“包含历史”由用户显式选择，历史回答注明当时/当前与失效状态。私有附件无可用解析文本时只列资料名，不宣称已理解其内容。

- [ ] **步骤1：写失败测试。** 当前与失效接口约定并存时优先当前；无资料时拒绝编答；历史模式可比较两次决策；检索不返回其他项目内容或草稿；来源中的越权提示不能改变查询范围。
- [ ] **步骤2：运行。** `python -m pytest backend/tests/test_student_knowledge.py -k 'search or answer' -q`，预期检索/回答未实现。
- [ ] **步骤3：实现。** `GET /api/projects/{id}/knowledge/search`返回可核对片段；`POST /api/projects/{id}/knowledge/answers`接收query与history选项。模型只得到已授权片段，回答结构为answer、citations、unresolved；引用ID、版本和引文必须存在且对应本次检索，失效或冲突时要求人工澄清，不写入业务结论。
- [ ] **步骤4：验证降级和陈旧响应。** 使用MockTransport覆盖超时、无效JSON、补造引用、引用文字不匹配、调用中知识版本变化；失败显示检索片段和明确状态。前端切换项目后旧回答不可进入新项目，追问必须继续绑定原项目。
- [ ] **步骤5：提交。** `feat(问答): 提供有来源的项目知识与历史查询`。

## 任务3：规则事实与Agent协作诊断

事实构造器`build_diagnostic_facts(analytics)`只接受P0已核对数值，输出稳定fact_id、指标值、单位、适用日期/成员、相关task_ids、project_revision和依据。必覆盖超容量、逾期、未完成前置、材料缺口及日志未知；没有风险时不编造建议。

固定样例：成员容量8h，本周任务分配12h，应产生超量4h的事实，点击能定位对应任务。模型不负责重新算数字。

- [ ] **步骤1：写失败测试。** 12/8得到4，已完成任务不占容量，容量0有文本，未知实际工时不能推断效率差；每条fact_id及任务集合可回到P0数据。
- [ ] **步骤2：运行。** `python -m pytest backend/tests/test_student_diagnostics.py -k facts -q`，预期事实构造器未实现。
- [ ] **步骤3：实现规则层。** `POST /api/projects/{id}/analytics/diagnostics`默认mode=rules，返回事实和人工处理入口，调用模型次数为0。UI展示时间、范围和“计算依据”，不生成风险概率或个人能力分数。
- [ ] **步骤4：实现可选解释。** 用户显式选择mode=explain才调用现有服务端模型。数值、成员、任务、日期由服务器按fact_id渲染；AI补充解释/追问标为建议，返回的fact_id/action必须在允许集合。缓存按项目/用户范围、修订号、日期、事实指纹、模型和提示版本分隔；加载、筛选和刷新不自动请求模型。
- [ ] **步骤5：提交。** `feat(诊断): 将真实风险事实与可核对AI解释关联`。

## 任务4：追问、调整和复盘草案衔接

诊断输出结构独立为title、summary、fact_ids、questions、recommended_actions；知识问答也独立于旧AgentOutput。允许动作只有查看任务、查看求助、核对资料、进入调整草案和生成本人复盘草案。所有写入继续走原权限与确认接口。

- [ ] **步骤1：写失败测试。** 伪造fact_id拒绝；模型建议改变教师截止日期不执行；旧revision结果标过期；成员不能通过建议修改他人排期；AI复盘不能自动作为本人确认报告。
- [ ] **步骤2：运行。** `python -m pytest backend/tests/test_student_diagnostics.py -q`与`node --test frontend/tests/studentDiagnostics.test.mjs`，预期新衔接行为缺失。
- [ ] **步骤3：实现。** DiagnosticPanel展示最多3条优先事实和追问；调整动作进入当前项目既有草案流程，带修订号检查，组长确认后发布。本人复盘先读取STU-03证据生成草稿，经本人核对后保存；模型不能新增未发生的成果或协助记录。
- [ ] **步骤4：验证异常。** 60秒有界超时、非法结构、预算/供应商失败、同请求重复和项目切换有明确状态；失败保留规则事实与手动表单，不循环重试或切付费模型。
- [ ] **步骤5：提交。** `feat(协作AI): 衔接有依据的追问调整与复盘草案`。

## 任务5：新能力评价与端到端验收

新知识/诊断任务与旧任务规划评价不同，指标不直接比较。实施时先固定独立开发与评价样例、输入和评分规则，再决定是否执行真实模型评价；计划编写阶段不生成“实测成功率”。

- [ ] **步骤1：写端到端失败场景。** 新两组项目分别完成“需求→分工→日志→求助→交付退回重提→同伴通过→阶段提交→知识确认→问答/诊断→复盘”；教师只能看到允许的公开结果。
- [ ] **步骤2：运行离线模拟。** `python -m pytest backend/tests/test_student_end_to_end.py -q`以及新前端测试，先看到未实现场景失败，再补齐实际缺项。
- [ ] **步骤3：记录新评价规则。** 评价引用存在/匹配、当前与历史区分、无依据拒答、事实数值一致、权限隔离、响应耗时和实际请求费用。规则模板/检索输出作为基线，与有模型解释组使用相同输入；所有失败计入分母，未知费用保持未知。
- [ ] **步骤4：执行允许的验证。** 离线MockTransport默认运行；真实调用需要用户当轮授权和免费型号/额度/预算预检，使用新目录保存冻结样例、被测源码、全部结果与失败，不改旧实验。出现越权或伪造来源的必过场景失败就不开放相应能力。
- [ ] **步骤5：提交。** `test(学生端): 验证分析协作与知识诊断完整流程`，为旧Agent可靠性与新问答/诊断分别报告结果。
