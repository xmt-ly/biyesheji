# 学生端深化与数据可视化开发总计划

> **面向 AI 代理的工作者：** 实际开发时使用 subagent-driven-development 或 executing-plans 逐任务执行子计划。本次只记录待开发范围和计划，不启动实现。

**状态：** planned（全部功能待开发）；开始整理：2026-10-19；完成整理：2026-10-20。

**目标：** 将学生端深化为“个人行动入口、团队协作、项目数据分析和有依据的智能辅助”相互衔接的系统，让普通成员持续参与，并形成可核对的答辩数据。

**架构：** 沿用当前 FastAPI、SQLAlchemy、SQLite、Vue 3 和手写 CSS。先建设指标与历史记录，再实现仪表盘和图表联动，随后扩展交付互审、求助、工作日志和知识问答；关键业务状态由授权人员确认，模型只提供可核对的辅助。

**技术栈：** 现有 Python 3.12、FastAPI、SQLAlchemy 2、Vue 3、JavaScript、Vite；计划增加 Apache ECharts 6.1.0，按需加载标准统计图，甘特依赖交互使用项目内 SVG 组件。图表均提供对应数据表。

## 4. 数据和指标契约

### 4.1 共同规则

- 统计以当前项目为基本边界。日期筛选使用 Asia/Shanghai，数据库时间保留带时区的时间戳；响应附 `as_of`、`project_revision`、筛选条件和指标版本。
- 每个指标同时返回计数/分母或数值、单位、计算说明及可下钻对象。前端显示值与下钻集合共用同一筛选口径。
- 日志、快照、事件和阶段提交是不同记录：计划发布快照不是每日执行历史；最后更新时间不是实际完成时间；预计/剩余工时不是实际投入工时。
- 空项目、零分母、零容量、缺日期、历史缺口分别表达。未知用 null/明确说明，不补零，不填造过去日期的观测点。
- 学生面板是团队内部分析；教师继续只访问允许的公开进度、计划和阶段成果，不获得聊天、内部卡片、求助细节、知识问答或私人工作日志。

### 4.2 指标口径

| 指标 | 定义及边界 |
| --- | --- |
| 任务完成比例 | `done任务数 / 全部任务数`，保留现有定义，不等于需求验收、教师通过或成员贡献 |
| 近期截止 | 所选日期起未来7天内到期且未done；逾期单列，边界含截止当天 |
| 逾期任务 | 截止日期早于所选今日且未done；已完成任务的历史延期另以完成事件分析 |
| 剩余工作量 | 未done任务的remaining_hours之和，展示这是填报/估算数值 |
| 成员周负荷 | 复用现有planning的工作日均分规则；纯周末任务归开始周，周容量为成员当前填写值，跨周独立比较 |
| 课程功能覆盖 | 必做功能中被已确认需求关联覆盖的去重比例；课程无必做功能时显示不适用 |
| 需求任务覆盖 | 已确认需求中至少有一项关联任务的去重比例；草稿不计入分母 |
| 关联任务已完成 | 对应需求的关联任务全部done；名称明确，不冒称需求已正式验收 |
| 实际工时 | 有效工作日志分钟数求和后转换小时；可回溯修订，不以进度差反推工时 |
| 估时偏差 | 对已交付任务比较原确认预计工时、最新计划预计工时和累计实际投入，分别展示；无日志则未知 |
| 阶段状态 | 各阶段最新提交版本的状态；旧版需要修改不覆盖新版通过 |
| 阶段返工 | 有教师退回或同伴退回事件的次数与版本依据，二者分开计数 |
| 个人贡献记录 | 本人交付、协助、验收和日志的证据集合，不生成按聊天数量或工时排名的能力分数 |

### 4.3 快照与趋势

每日快照保存项目修订号、当日观测时间、任务数量/状态、剩余工时、计划基线和成员周负荷。只记录服务实际观察到的日期；当天可幂等刷新，过去日期不从当前状态回填。显示采集起点和缺失区间。

燃尽图以明确选择的计划基线展示理想线和观测线；任务新增、移除、范围/工时调整作为范围变化标记。累计完成和每周新增/完成来自任务事件，不能把当前done数量平摊到过去。实际投入曲线只能从工作日志产生。

## 5. 业务与权限约束

1. 保留 `Task.status=todo/doing/done`，同伴验收状态放在独立交付记录，不直接向旧模型协议增加状态值。
2. 同伴验收按项目策略启用；旧项目默认沿用现有完成流程，未启用时可以保存交付草稿，但不能提交互审。启用后所有置done入口统一校验最新有效交付已通过。不能靠绕过页面、手动API或Agent发布跳过验收。
3. 组内其他有效学生可以验收，提交者不能自审；验收记录绑定成果版本和任务验收条件版本。更新成果必须新建版本，过期版本的通过不能批准新版本。
4. 提交交付不自动伪造进度百分比或实际工时。启用互审后，通过时原子地置done/100%/剩余0，退回时保留证据并由成员更新剩余工作。
5. 组长确认整体分工和计划；普通成员可提求助、接手协助、写日志、提交成果与互审，不因此获得更改他人排期的权限。
6. 知识/决策草稿和AI总结均有人类确认过程；当前结论与历史失效版本分别展示，引用可打开具体来源。
7. 仪表盘加载和筛选不自动调用收费模型。基础风险由确定规则计算；AI解释失败时保留原始数据与人工处理入口。

## 7. 总体验收场景

- [ ] 成员登录后从本人面板定位任务、待互审及求助，图表下钻与列表计数一致。
- [ ] 两名成员完成“交付v1→退回→v2→通过”，只有有效验收可完成要求互审的任务；本人自审、旧版本审核和重复操作被保护。
- [ ] 前端成员因接口受阻发起求助，另一成员接手、处理、提交解决说明，发起者确认；依赖风险与处理事件可追溯。
- [ ] 记录真实工作日志后可看估时偏差，修改日志保留版本；只有记录者能修改本人日志。
- [ ] 负荷热力图与既有排期检查对同一周给出一致的超量结论；容量0、跨周、纯周末和已完成任务覆盖。
- [ ] 甘特、矩阵、风险和时间线可定位同一任务，切换项目后旧请求和图表事件不污染新项目。

- 子计划中的`python`指当前项目已经验证的解释器。Windows示例为`& 'D:\Anaconda3\envs\face_env\python.exe' -m pytest ...`，云端示例为`PYTHONPATH=backend .venv/bin/python -m pytest ...`；不得在Windows无确认地使用系统Anaconda解释器。Node命令使用已验证的Node.js 24环境。
